<Insight eyebrow="The real question" title="Autonomy should scale with the action, not the model.">
The question that decides whether an action belongs to an AI agent isn't "is the model good enough." It's "is this action bounded and reviewable." Those are different questions, and answering the wrong one is how test automation AI ends up either too cautious to be useful or too permissive to be safe.
</Insight>

## The wrong question people ask first

Most debates about AI test automation get framed as a capability question: is the model smart enough yet to run a validation suite unsupervised? That framing produces two equally bad answers. Skeptics say no, not yet, hardware is too unforgiving for anything that can hallucinate — so keep everything scripted and keep a person on every run. Enthusiasts say yes, current models can already reason about test states well enough to run the bench themselves — so hand them broad access and let judgment do the rest.

Both answers chase the wrong variable. Model capability is real and improving, but it isn't what should decide which parts of a test workflow run autonomously. What should decide it is a property of the action itself: whether it's bounded and reviewable, or open-ended. That distinction holds regardless of which model is doing the reasoning, and it's the difference between autonomous testing that's operationally defensible and autonomous testing that's just "trust the AI" wearing a test report as a costume.

## What "bounded" actually means

A bounded action has four properties, and it's worth being precise about them because "bounded" gets used loosely too. It has a defined start and end — acquiring an interface and releasing it are both explicit steps, not implicit states someone assumes will get cleaned up. It sends only a message or command that was already approved — an encoded frame from an approved DBC, a pre-approved diagnostic request — never one typed or generated on the fly to fit the moment. Its next step is gated on an observed, decoded condition, not a fixed timer or a guess about how long something should take. And it ends by packaging a reviewable artifact — the trace, the decoded signals, the verdict — rather than a person's summary of what the AI said happened.

Acquire, capture, wait-on-a-decoded-condition, send-only-the-approved-message, release, package evidence: every one of those satisfies all four properties, which is exactly why they're the operations an agent can be trusted to sequence on its own. None of them requires trusting the model's judgment about what's safe to do — the boundary itself does that work. The model decides *when* to acquire, *which* approved message applies to the state it's observing, *what condition* to wait on. It never decides whether to acquire something outside the interface it was given, or whether to send something that wasn't already vetted.

## What isn't bounded, and why that's the actual line

Contrast that with the actions that don't clear the bar, and notice the pattern isn't "harder" or "requires more intelligence" — it's "open-ended." Raw shell access to test hardware is unbounded because there's no fixed catalog of what might get executed against it; the agent could, in principle, run anything. An agent composing its own commands instead of selecting from pre-approved ones is unbounded for the same reason, even if every individual command it invents happens to be reasonable — the point isn't that any one command is dangerous, it's that nothing constrained the space it drew from. And treating the model's own judgment as the acceptance criterion — "the agent reviewed the log and says it passed" — is unbounded because there's no decoded, observable signal backing the verdict; the pass/fail lives inside the model's reasoning instead of in something an engineer could independently check.

That's a more useful line than "let the smart model do the risky stuff." A sufficiently capable model doesn't make raw shell access safe, because the risk was never about whether the model could figure out the right command — it's that nothing external to its reasoning would catch it if it didn't. Conversely, a comparatively modest model can be trusted to sequence acquire/send/gate/release all day, because the guardrails don't depend on the model getting it right; they depend on the operations it's allowed to perform already being the safe subset.

## A framework worth applying, not just agreeing with

This gives validation teams something more actionable than a vibe. When evaluating a new use case for autonomous testing, don't start by asking how good the model is. Ask whether the action has a defined start and end, whether it can only send something already approved, whether its next step is gated on a decoded condition instead of a timer, and whether it ends in a packaged artifact a person can review. If all four hold, it's a reasonable candidate for autonomy regardless of which model is running it. If any don't, the fix isn't a better model — it's narrowing the action until it does.

That's also, not incidentally, the question a validation lead is actually asking when they hear "AI test automation" for the first time: not "how smart is it," but "can it safely do the specific thing my engineer does by hand." The honest answer depends on the shape of that action, not on the model behind it — a framework built around boundedness is the version of that answer that still holds up after the model has changed three more times.

<Insight eyebrow="Applying it" title="Narrow the action before you trust the model more.">
When an action fails the bounded test, the fix isn't a smarter model watching more carefully — it's redefining the action so it has a defined start and end, sends only what's approved, gates on a decoded condition, and ends in a reviewable artifact. Get the boundary right and the autonomy question mostly answers itself.
</Insight>
